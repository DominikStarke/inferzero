What 2026-11-26 added (the 125H, Windows, oneDNN 3.14.2 built there, the 4B at 512 x 2560 -> 9216):
- **oneDNN's int8 speed depends on the scales.**
  - With one scale per token and per column, it runs 12.1 TOPS. That's H8R's case: our H8R GEMM runs 8.7 TOPS, so
    the comparison in item 3 is fair for H8R.
  - With a scale per 32 weights, as GGUF's W8 form needs, oneDNN runs 3.1 TOPS. Our W8 GEMM runs 7.9 TOPS there.
  - So the gap to close is H8R's tile (71 % of oneDNN). Dropping the scales gained only 7 %, so the tile's DP4a issue
    and loads are the limit.
- **H8 is on by default on Xe-LPG for the Qwen3.5 dense models** (release 2026.11.26.03). It runs 3-5 % faster on 4K
  prompts, and the 4B's KL goes 0.0122 -> 0.0017. Short prompts lose on just-in-time models (the 9B: -16 to -29 %
  under 1K tokens): each chunk decodes and rotates its weights again. Next steps:
  - decode straight into the rotated form, one kernel;
  - fuse the rotation into the norm for 1,024-value blocks without the spill (42 scratch messages on mtl today).
- **A large context costs speed.** `--ctx auto` reserves 262K on the 4B (10.84 GiB of GPU buffers). Against 16K-128K
  (7.0-8.8 GiB), it's 4.5 % slower on the prompt and 2 % slower per generated token. It's a step above 128K, not a
  slope: flat from 16K to 128K. No single buffer is near 4 GiB (the KV is per layer, ~0.5 GiB each), so the cause is
  likely the total mapped size (page tables, Windows residency), not yet proven. Two ways to fix it:
  - an iGPU cap on `--ctx auto` at 128K, small and user-facing;
  - a KV cache that grows with the conversation instead of being reserved up front, a design change.

  First check whether allocating the KV before the weights moves the step.

## 5a. The server for use from other machines: a reverse proxy, the web UI off (the user, 2026-11-27; #102)

Today `serverz` has no authentication. On any address other than localhost it only warns that anyone who can reach it
can use the model (`tools/server.cpp:2722`). zchef2k (#102, 2 x A770 in a rootless container) put nginx in front to
require a bearer key, allow only the `/v1` endpoints and rewrite the `Host` header.

**No `--api-key` in inferzero** (the user, 2026-11-27, after weighing it). The reverse proxy does the key, TLS and the
network, so the security work stays with nginx / Caddy and the OS:
- a key without TLS is readable on the network, so a built-in `--api-key` would invite the unsafe setup
  (`--host 0.0.0.0 --api-key ...`, no proxy) and give a false sense of safety;
- vLLM's own security docs show the trap: its `--api-key` covers only `/v1`, other routes run inference without it,
  and the docs end up telling users to put a proxy in front and "not rely exclusively on --api-key"
  (docs.vllm.ai/en/latest/usage/security);
- an API key is still security code to own: where it's read from, that it never reaches a log, a crash report or
  "Copy for an issue", and the 401s.

What inferzero does instead: `--no-webui` (below), which shrinks what's served, and a production note in USAGE.md
with the proxy's config.

**The web UI off, for production** (zchef2k, #102, 2026-11-27; decided by the user the same day, option B: "if locally, I want it to stay as it is; launcher should have this option". Sent to the Developer as fix/api-only, with the launchers' option and the clearer 403 texts, for the next release, not Monday). Today `serverz` always serves the web UI
at `/` (`tools/server.cpp:388`). `--no-web-tools` only turns off the model's web search and fetch tools. The plan:
- **`--no-webui`** (and `INFERZERO_NO_WEBUI=1`): `/` and the UI's own endpoints answer 404 (the files, projects,
  terminal, MCP and sessions pages). Only the OpenAI-compatible `/v1/*`, `/health` and `/props` stay.
- **Server-side tools off by default with `--no-webui`:** the terminal, files and MCP tools the web UI drives can't be
  reached through the API. Say which stay (`/v1/*` with tool calls defined by the client is unaffected).
- **One start line** lists what is served: "API only: /v1/*, /health, /props (--no-webui)".
- **A short "production" note in USAGE.md:**
  - inferzero stays local-first: for use from other machines, **a reverse proxy in front** (nginx or Caddy, with an
    example config) does TLS and faces the network. Its security updates are its own team's and the OS's, not ours;
  - `serverz` listens on 127.0.0.1, and the proxy forwards to it with `Host: 127.0.0.1` (the normal setup, not a

  - the proxy's key check, TLS and `Host: 127.0.0.1`, in one example config each for nginx and Caddy;
  - `--no-webui` together with `--slots N`;

## 5b. Images decoded without ffmpeg, on the GPU where it pays (the user, 2026-11-27; #104)

Today `src/image.h` decodes on the CPU: Windows through the Windows Imaging Component, Linux through an `ffmpeg` child
process (a PPM on a pipe), then a Pillow-compatible bicubic resize (`resize_bicubic`, :159) to the vision encoder's
size, also on the CPU. #104: our Docker image had no ffmpeg, so image requests failed there (ffmpeg is now in the
image, main 8770658). The goal is no external program for images on any OS, and the parallel parts on the GPU.

What can go to the GPU, by format:
- **JPEG** (most photos and screenshots sent by clients):
  - Huffman (entropy) decoding is serial within a scan, so it stays on the CPU unless the file has restart markers.
  - Dequantization, the 8 x 8 inverse DCTs, chroma upsampling and YCbCr -> RGB are parallel: a good GPU kernel,
    followed straight by the resize and the encoder's normalization, so the pixels never come back to the host.
  - Intel's media engine also decodes JPEG in hardware (VA-API on Linux, D3D11 / Media Foundation on Windows), but
    that's a second API and a new dependency next to Level Zero. Measure it before choosing it.
- **PNG** (screenshots, diagrams): deflate is serial, so it stays on the CPU. The un-filtering per row is cheap. An
  in-process deflate decoder removes ffmpeg for PNG.
- **The resize and normalization** are parallel for every format, and the encoder already runs on the GPU. A GPU
  bicubic kernel must match `resize_bicubic` bit for bit, or within the vision KL check where it can't.

The steps, in order:
1. **Measure the share:** CPU decode + resize time against the encoder's GPU time for a typical image (a 1080p JPEG
   screenshot, a 4K photo). If decoding is a few ms against an encoder of hundreds, the GPU step only pays for big
   images or many pages (OCR of a PDF, Xiaomi OCR at ~10K tok/s on discrete cards, #103).
2. **In-process decoders** for JPEG and PNG on Linux, so the Docker image and plain Linux installs need no ffmpeg for
   images (audio and video keep it). A small, permissively licensed decoder, or our own baseline JPEG + inflate, with
   the same pixels as the Windows path (checked on a set of test images).
3. **The GPU part:** the resize and normalization first (every format), then JPEG's IDCT and color conversion. Exact
   against the CPU path, measured per image size.

## 5d. Image generation: FLUX.2 [klein] 4B (the user, 2026-11-27)

A diffusion model for images, run inside inferzero as an engine of its own, the way Whisper is
(`zero/whisper_engine.h`, `whisper.cl`, `tools/ref_whisper.cpp`), not as a language model under CONTRIBUTING.md
section 3.

**The model** (from its model cards; check each point against Black Forest Labs' own card before writing code):
- a rectified-flow image transformer of ~4B parameters, open weights under Apache 2.0;
- a Qwen3-4B text encoder (36 layers, 2,560 wide);
- a VAE decoding 32 latent channels to pixels.

**Why inside inferzero:**
- the text encoder is a Qwen3 model, which the engine already runs (Qwen3-ASR's text model): a prompt pass that
  returns hidden states instead of logits;
- each denoising step is a pass of the transformer over all image tokens, thousands of rows: prompt-shaped GEMMs,
  where the engine is strongest. The f16 XMX GEMM (`gemm_x16.cl`) and the attention kernels exist;
- the server, web UI, launchers, release pipeline, GPU guard and kernel cache come with it.

**What is new:**
- the image transformer (`zero/flux_engine.h`), its kernels in a file of their own (`flux.cl`);
- the VAE decoder: convolutions, upsampling, norms;
- the flow-matching sampler: the step schedule, guidance where the model uses it;
- an f32 reference: `tools/ref_flux.cpp`, from the model's own modeling code.

**The steps:**
1. **Read the model:** its file formats (safetensors, GGUF quantizations people publish), the transformer's blocks,
   the text encoder's output it takes, the VAE, the sampler's steps. Write `docs/flux2.md` with what each part needs
   and which existing kernels cover it.
2. **Correctness on one GPU:**
   - the text encoder through the Engine, against `ref_forward`;
   - one denoising step against the f32 reference (relative error, worst value);
   - then a whole image against the reference's image: PSNR, and the same image from the same seed run to run.
3. **The server:** OpenAI's `/v1/images/generations` (size, steps, seed); the web UI's image tab; the launchers
   downloading it like the other models.
4. **Every GPU kind and weight type** the published files use (f16 / bf16 / Q8_0 / 4-bit), and speed per image at
   512 / 1024 pixels against stable-diffusion.cpp or ComfyUI on the same card.
5. **Later:** several GPUs, and the speed work (fusing the transformer's steps, H8 for its GEMMs if the image quality
   holds).

**Not in this item:** diffusion language models (LLaDA, Dream). Those are text models with a different generation
loop, and would go through CONTRIBUTING.md section 3 as a new model with its own generation mode.

Nothing is built until the user approves the design in `docs/flux2.md`.

   launcher, in place of the lists each keeps today (the sweep's own, `best-setups.tsv`, `options.tsv`). A row per
   switch:
   - its values;
   - the GPU kinds and models it applies to;
   - bit-identical or logits-moving (then KL-checked);
   - its memory cost;
   - user-facing, or internal / experimental (hidden);
   - what it does, in one plain sentence;
   - **its effect so far, per GPU kind** (the user, 2026-11-26: "and how each switches effects so far"): the measured
     change in prompt and generation speed and in KL on each card it ran on, with the issue or before-after row as
     the source; "not measured" where nothing is. Filled first from `docs/before-after.md` and the sweeps posted on
     GitHub (#4, #12, #45, #48, #60, #92, #99 and the others), then kept current from the tuner's saved results
     (step 7).

   **A switches glossary is generated from it** (the user, 2026-11-26: "it should have like switches glossary"): a
   docs page listing every switch with its plain sentence, values, the GPUs it applies to, exactness and the evidence,
   grouped by what it touches (prompt GEMMs, generation, attention, DeltaNet, MoE, memory, multi-GPU, drafting).
   `runz --switches` prints the same for this GPU and model, and the launcher shows the user-facing part. Since all
   three come from the registry, the glossary can't go stale.

   The engine warns about a switch it reads that has no row, so a new one can't slip in without it. Most of the 343
   end up hidden, which by itself cuts what users see to a handful. The launcher redesign's `options.tsv` (step 1)
   then reads its rows from the registry instead of keeping its own.
1. **The tuner is in the engine,** not a script: `--tune` in runz and serverz, and the launcher's first start of a model
   offers it. It runs the sweep's generation, prompt and tile phases (and the MoE one for an MoE model) for this GPU,
   driver and model, in short runs (`--bench-pp 512 / 4096`, tg128).
2. **Only bit-identical settings win on their own.** Each candidate's logits are hashed against the defaults. A setting
   that moves the logits is never picked automatically: it needs the KL check against f32, which the tuner can't run
   without the reference.
3. **A short candidate list, not all 343:** the switches that won on some card in the users' sweeps (#4, #45, #48,
   #60, #92, #99), their values, and the tile per GEMM kind. Target 10-20 minutes. The full sweep stays the script.
4. **Noise handled as the sweep's C phase does:** the order A B B A, a 2 % bar, the defaults run first and last to
   catch drift. a1ex4's 140V (#60) dropped to a third of its speed in single runs, which shows why.
5. **Saved per GPU, driver and model:** `%USERPROFILE%\.inferzero\tune\<GPU id>-<driver>-<model file hash>.json`
   (settings, numbers, engine commit).
   - Applied at every later start, with one log line naming the settings and their measured gain.
   - Tuned again when the driver, the release or the model file changes.
   - `--no-tune` / `ARC_TUNE=0` runs the defaults; an `ARC_*` set by hand still wins.
6. **Safety:** a setting that hangs, fails or spills is dropped and remembered. On the laptop every tuning run goes
   through `bench\gpu_guard.ps1`; after a hang, no GPU work until a restart.
7. **Fewer switches over time:** users can send the saved results (opt-in, as the test scripts' zip). A GPU kind's
   defaults then come from them, and a switch that wins nowhere is deleted. That is the shared-GEMM design's rule (old
   routes go once new ones cover them, docs/design-shared-gemm.md §6.0), and its fitted selection model (§3.5) later
   chooses the GEMM tiles instead of switches.
8. **The launcher's setup page, after the launcher redesign:** a "Tune for this PC" button that runs the engine's
   tuner, and the few user-facing options, both from the registry. It does no benchmarking of its own. The Linux and
   Windows launchers get it alike.
